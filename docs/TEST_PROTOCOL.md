# Протокол проверки расчёта

Как убедиться, что ядро считает правильно, и как воспроизвести каждое число из
документов. Запуск всего протокола: `python -m pytest`, около двух минут, нужен
только Python 3.10+ и `pytest`.

## 1. Что подаётся на вход

| Вход | Где лежит | Кто задаёт | Проверка |
|---|---|---|---|
| Данные кейса: спрос, каналы, хранилища, инвестиции, ограничения | `data/*.csv` | организаторы, не редактируются | `meta.data_hash` в каждом результате; тест `test_extension.py` показывает, что копия с правками даёт другой хэш |
| Сценарии | `configs/scenarios/*.yaml` | `base`, `mandatory_stress` от организаторов, `team_*` от команды со статусом `TEAM_ASSUMPTION` | `test_yaml.py`: разбор YAML, обязательные поля, маркировка командных сценариев |
| Допущения команды | `configs/assumptions.json` | команда, каждое со статусом и основанием | `test_engine.py::test_discount_rate_override_changes_pv_only` и другие |
| План оператора | JSON по `docs/CONTRACT.md`, примеры в `results/plans/` | команда или пользователь интерфейса | `test_plan_validation.py`: 19 проверок ввода, включая примеры организаторов из `tests/reference/invalid_plan_examples` |
| Реестр рисков | `configs/risks.json` | команда | `test_risks.py` |

## 2. Порядок расчёта

Один вызов `calculate(case, scenario, plan, assumptions)` делает по шагам:

1. проверка плана: форма, типы, известные каналы и годы; при ошибке расчёта нет;
2. доступность каналов и хранилищ по годам и месяцам: `available_from`,
   Earth-New через 24 месяца после исполнения опциона, ISRU с марта 2038 при
   полном финансировании, ZBO с года оплаты;
3. поставка по каналу за год: заказ, ограниченный бронью и мощностью, умноженный
   на долю поставки из сценария; превышения не режутся молча, а становятся
   нарушениями;
4. помесячный баланс бака: приход, потери от прихода, выдача сначала
   критическому спросу, потом остальному, остаток; переполнение и дефицит
   отдельными строками;
5. деньги по годам: закупка с take-or-pay, брони, хранение по среднему запасу,
   фиксированный OPEX, CAPEX, стартовый запас; PV по ставке из допущений;
6. проверки: все строки `data/constraints.csv` плюс технические; `feasible`
   равно «ни одна жёсткая проверка не провалена».

Подробно про формулы: [ARCHITECTURE.md](ARCHITECTURE.md), про поля результата:
[CONTRACT.md](CONTRACT.md).

## 3. Что проверяется на выходе

### 3.1. Контрольные примеры организаторов

`tests/test_reference.py`, десять векторов V01–V10 из `tests/reference/expected_checks.json`:
материальный баланс, дефицит без отрицательного запаса, take-or-pay и его
однократность, пропорциональная бронь, потери один раз от прихода, резерв 45
дней, превышение мощности, вложенность критического спроса, запрет повторного
умножения стрессовой поставки ISRU на reliability. Ожидаемые значения сравниваются
через `pytest.approx` (относительная точность 1e-6).

### 3.2. Инварианты на случайных планах

`tests/test_random_plans.py`: 60 случайных планов (`random.Random(seed)`,
seed 0…59, генератор в том же файле) считаются в обоих сценариях организаторов.
Для каждого проверяется:

- баланс каждого года: открытие + поставка − потери − выдано − остаток = 0,
  остаток не отрицательный;
- цепочка лет: остаток года равен открытию следующего;
- потери равны приходу × ставка хранилища, критическая выдача не больше общей,
  спрос года равен спросу сценария;
- по каждому каналу: поставка не выше мощности, заказа и брони с учётом месяцев
  доступности; факт равен плану × доля сценария; платёж равен оплачиваемому
  объёму × цена; недоступный канал не платит бронь;
- итог года равен сумме статей, PV равен итогу × коэффициент;
- `feasible` равно отсутствию жёстких нарушений, у каждой проверки `ok`
  согласован с `excess`, год внутри горизонта;
- в JSON нет `NaN` и `Infinity`, в длинной выгрузке только числа.

Плюс повторяемость (два расчёта одного плана дают один байт в байт JSON) и
цены стресса: у Core и Flex в 2038–2039 ровно ×1,25 на 20 планах.

### 3.3. Правила кейса по одному

`tests/test_engine.py`, 54 теста, каждый на одно правило. Примеры:
Earth-New доступен с 2038 и в первый год с reliability; ZBO переключает ёмкость
и потери с января года оплаты; ISRU без финансирования до 2038 не считается;
Emergency не более двух лет подряд базовым каналом; резерв ровно 45 дней проходит;
бронь Emergency засчитывается в резерв только когда запас покрывает 42 дня
ожидания; при дефиците сначала выдаётся критический спрос; CAPEX-лимиты 2037 и
2040; в стрессе спрос только с 2038, цены только у Core и Flex, потолок потерь
только с 2038; `constraint_profile` делает правила базы жёсткими в сценариях
команды.

`tests/test_rules.py`: 12 тестов чистых формул из `src/fuelhub/rules.py`.

### 3.4. Ввод, выгрузка, интерфейс

- `tests/test_plan_validation.py`: 19 тестов ошибок ввода, включая примеры
  организаторов; все ошибки собираются в один ответ.
- `tests/test_export_cli.py`: длинный CSV равен результату, XLSX читается
  обратно, CLI и API дают один результат, две выгрузки байт в байт равны.
- `tests/test_server.py`: 11 тестов HTTP: расчёт совпадает с CLI, невалидный план
  даёт 400, сохранение и загрузка, выгрузка трёх форматов.

### 3.5. Стратегия и документы

- `tests/test_candidates.py`: рекомендуемые планы v3-* исполнимы в стандартном
  сценарии с резервом не ниже 55 дней с 2036, их ответы исполнимы в стрессе без
  дефицита, ответы меняют только Flex и Emergency 2039–2040, базовый план один
  стресс не проходит, рекомендуемый план дешевле ручного base-v1, запас по
  резерву стоит меньше 100 PV.
- `tests/test_tools.py`: инструменты `tools/`: старый ответ нарушает срок
  реакции, чувствительность меняет только 2038–2040 и совпадает с ядром,
  оптимизатор возвращает план, который читается ядром.
- `tests/test_risks.py`: реестр рисков полный, попадает в результат, каждый
  риск без мер и с мерами ведёт себя как в `docs/RISKS.md`, подготовки не ломают
  стандартный сценарий и укладываются в один план, R6 считается на копии данных.
- `tests/test_extension.py`: копия данных с 2041 годом и новым каналом
  считается без правок кода, лимиты организаторов на копии действуют.

## 4. Точность и допущения проверки

- Внутренний шаг месяц, спрос года делится на 12 поровну; поставка делится
  поровну на месяцы доступности канала (у Earth-New и ISRU их может быть
  меньше 12).
- Сравнения чисел: `pytest.approx` с относительной точностью 1e-6, для сумм
  абсолютная 1e-5.
- Резерв проверяется на 1 января каждого года по требованию организаторов.
- Дефицит не имеет цены, поэтому ограничения жёсткие, а не штрафные.

## 5. Воспроизведение чисел из документов

```
python -m pytest
python -m fuelhub calc results/plans/v3-earth.json
python -m fuelhub calc results/plans/v3-earth.json --scenario MANDATORY_STRESS
python -m fuelhub calc results/plans/v3-earth-response.json --scenario MANDATORY_STRESS
python -m fuelhub compare results/plans/v3-earth.json
python tools/compare_plans.py
python tools/compare_plans.py --plans v3-earth v3-full v3-lunar base-v1 --scenarios BASE TEAM_LOW_DEMAND TEAM_HIGH_DEMAND MANDATORY_STRESS TEAM_GEO_PRICE --out results/comparison_demand.csv
python tools/check_response.py v3-earth v3-earth-response
python tools/sensitivity.py v3-earth --scenario BASE
python tools/sensitivity.py v3-earth-response --scenario MANDATORY_STRESS
python tools/risks.py
python tools/optimize.py --iters 15000 --seeds 3 --margin 10 --tag v3
```

Последняя команда идёт заметно дольше остальных (три старта по 15 000 итераций на стратегию) и пересоздаёт планы `v3-*`; остальные
считают секунды. Числа в `docs/STRESS_RESPONSE.md` и `docs/RISKS.md` взяты из
файлов `results/comparison*.csv`, `results/sensitivity_*.csv`,
`results/risks_assessment.csv`.
