# Архитектура расчёта и дорожная карта решений

Один документ на два вопроса жюри: как устроен цифровой контур (критерий 6) и
когда какое решение принимается в рекомендуемом плане (критерий 9).

## 1. Схема

```
 организаторы                    команда                          пользователь
 ────────────                    ───────                          ────────────
 data/*.csv ─────────┐
   demand            │
   supply_sources    │     configs/assumptions.json
   storage_options   ├──► CaseData ◄── (12 допущений, каждое с источником)
   investment_options│        │
   constraints       │        │            план JSON ◄── интерфейс / CLI / results/plans
 ────────────────────┘        │                │
 configs/scenarios/           ▼                ▼
   base, mandatory_stress ─► Scenario ─► Engine.run(plan, scenario)
   (правки чисел кейса из интерфейса: overrides → копия CaseData, хэш +суффикс)
   team_* (TEAM_ASSUMPTION)                    │
                                               │  1 доступность каналов и хранилищ по месяцам
                                               │  2 поставки: заказ ∧ бронь ∧ мощность × доля сценария
                                               │  3 бак по месяцам: приход → потери → выдача → остаток
                                               │  4 деньги по годам, PV
                                               │  5 проверки: constraints.csv + технические
                                               ▼
                                            Result ──► экран (app/static)
                                               │  ──► CSV длинный / XLSX по листам
                                               │  ──► tools/: сравнение, чувствительность,
                                               │             риски, оптимизация, проверка ответа
 configs/risks.json ───────────────────────────┘  (прикладывается как есть)
```

Единственный источник чисел: `src/fuelhub`. Интерфейс, CLI, инструменты и
тесты вызывают одну функцию `calculate(case, scenario, plan, assumptions)`.
Формулы лежат в `src/fuelhub/rules.py` (чистые функции, 12 тестов), логика
времени и контрактов в `engine.py` (`Engine.availability`, `source_years`, `run`, `finance`), проверки в `Engine.constraint_checks`.

## 2. Формулы и откуда они

| Величина | Формула в модели | Источник | Где в коде |
|---|---|---|---|
| Остаток | `I_end = I_start + Q_delivered − Losses − Q_served`, по месяцам | CALCULATION_RULES §1 | `rules.closing_inventory`, `Engine.run` |
| Дефицит | `max(0, Demand − Q_served)`, отдельно общий и критический; сначала выдаётся критический спрос | §2, §7 | `rules.serve` |
| Потери | `gross_inflow × loss_rate` один раз от прихода месяца; ставка по активному хранилищу | §3 | `rules.losses_on_throughput` |
| Резерв 45 дней | `R_y = D_y × 45 / 365`; проверка физического запаса на 1 января; бронь Emergency засчитывается, если запас покрывает 42 дня ожидания и бронь не меньше недостачи | §4, FAQ; допущение `emergency_wait_days` | `rules.reserve_requirement`, `Engine.aggregate` |
| Take-or-pay | `Q_pay = max(Q_actual, share × Q_reserved)`, `Variable = price × Q_pay`; второй платёж не добавляется | §5; допущение `variable_payment_basis = actual_delivery` | `rules.payable_volume` |
| Бронь | `rate × reserved × period_fraction`, доля года по месяцам доступности, не дублируется по месяцам | §6, §15 | `rules.reservation_payment` |
| Сервис | `served / demand`, при нулевом спросе 1,0 | §7 | `rules.service_level` |
| Стоимость | `Procurement + Reservation + Holding + FixedOPEX + CAPEX + стартовый запас`; хранение по среднему запаса начала и конца месяца × ставка / 12 | §8; допущение `holding_cost_basis` | `Engine.finance` |
| PV | `CF_t / (1 + r)^(t − 2035)`, r = 8 % | §9; допущение `discount_rate` | `rules.discount_factor` |
| Шаг | месяц; спрос года поровну по 12 месяцам; поставка поровну по месяцам доступности канала | §10; допущение `intra_year_profile` | `Engine.run` |
| Срок заказа | `order_by` = первый месяц поставки минус lead time (Emergency 6 недель → 1,4 месяца) | §10; допущение `weeks_per_month` | `Engine.order_by` |
| Reliability | в стандартном сценарии не множитель; в стрессе доли ISRU 0,55 / 0,75 берутся как есть | §11, STRESS_PROTOCOL | `scenario.delivered_share` |
| Earth-New | опцион 90 в год опциона, исполнение 270 в год исполнения, поставки через 24 месяца после 1 января года исполнения | §12; допущение `earth_new_commissioning_months` | `Engine.availability` |
| ISRU | 1 250 равными долями по годам финансирования, все до 2038; первая поставка март 2038 | данные; допущение `isru_lead_months` | `Engine.availability` |
| ZBO | 180 в год оплаты, с 1 января этого года ёмкость 120 т и потери 1,2 % | данные; допущение `zbo_commissioning` | `Engine.availability`, `storage_at` |
| Проверки | все строки `constraints.csv` с их `severity`, плюс технические: мощность, бронь, ёмкость бака, доступность, финансирование ISRU | §13, §14 | `Engine.constraint_checks` |

Каждое допущение команды лежит в `configs/assumptions.json` со статусом,
единицей, источником и полем `scope`, где написано, на какой выход оно влияет.
В результате расчёта `meta.assumptions` повторяет их, `meta.data_hash` фиксирует
данные, `meta.plan` сам план: из одного файла результата видно всё, из чего он
посчитан.

## 3. Что в модели не считается

- Выручка и цена дефицита: организаторы их не задали, поэтому ограничения
  сервиса и резерва жёсткие, а не штрафные.
- Вероятности отказов: reliability в данных не превращается в множитель;
  риски считаются сценариями и интервалами (`docs/RISKS.md`).
- Орбитальная механика и окна пусков: год и месяц поставки берутся из lead time.

Что видно из карты:

- Все инвестиции сделаны к 2037, CAPEX 540 против лимитов 1 800 к 2037 и
  2 800 к 2040.
- Точек, где решение нельзя отыграть, три: опцион 2035, исполнение 2036 и заказ
  Earth-New на 2038 в январе 2036. Дальше план живёт заказами с горизонтом
  год, и каждый год есть Flex с четырьмя месяцами и Emergency с шестью неделями,
  чтобы поправить объём.
- Реакция на стресс укладывается в три заказа. Подготовки из реестра рисков
  (брони Flex и Emergency, ZBO на год раньше) добавляют к базовому плану
  214 PV, проверка `tests/test_risks.py::test_all_preparations_fit_together`.
