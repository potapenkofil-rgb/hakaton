# Frontend: создание и расчёт сценария

## Запуск

Из корня проекта в PowerShell:

```powershell
$env:PYTHONPATH = 'src'
python -m fuelhub serve
```

Открыть http://127.0.0.1:8765. Если WindowsApps подменяет `python`, используйте полный путь к рабочему Python 3.10+.

## Состояние и последовательность

- `state.inputs` — справочники из API. `state.plan` — единственный применённый черновик в существующем формате ParticipantPlan. Название хранится в `label`, технический идентификатор — в `plan_id`.
- Формы отображают черновик и записывают изменения обратно. Исходный импортированный JSON сохраняется целиком до редактирования формы; структурно некорректный JSON исправляется отдельным текстовым редактором, без тихого удаления неизвестных строк.
- `revision` изменяется при правках. `validatedRevision` разрешает расчёт только проверенной версии. Правки сбрасывают проверку и результат. Неприменённый текст JSON отдельно помечен `rawDirty` и блокирует расчёт.
- `state.result` появляется только после успешного `/api/calculate`. Входной экран не открывает автоматически `base-v1`. Результаты и сравнение скрыты до расчёта; ответ устаревшего запроса не принимается.
- Состояния: EMPTY, LOADING, DRAFT, READY, VALIDATION ERROR, CALCULATING, SUCCESS, ERROR. Ошибка сети допускает повтор действия; INVALID_PLAN требует исправления и повторной проверки.
- Переключение BASE / MANDATORY_STRESS в результатах пересчитывает тот же ранее проверенный план; редактирование решений возвращает к проверке.

## API и границы модели

Используются `GET /api/inputs`, `GET /api/plans/{id}`, `POST /api/plans`, `POST /api/calculate`, `POST /api/compare`, `POST /api/export?format=csv|xlsx&scenario=…`.

Отдельного HTTP endpoint проверки нет. `validation.js` выполняет предварительную проверку типов, идентификаторов, годов, дублей и неотрицательных объёмов по структуре `configs/schemas/plan.schema.json` и правилам ввода `src/fuelhub/plan.py`. Backend остаётся окончательным валидатором. Исполнимость, мощности, поставки и финансовые ограничения frontend не рассчитывает.

Период, спрос, тарифы и стоимости инвестиций заданы данными кейса, а не произвольными полями плана. В карточке показывается начальный запас, а не рассчитанный резерв. Показатели и пункты меню о количестве и лимите запусков удалены. «Логистика и сроки» показывает существующие сведения о доступности каналов и размещении заказов. Поиск охватывает разделы интерфейса. Недоступные до расчёта разделы видны в выдаче, но заблокированы. Сохранённые планы открываются отдельной командой «Открыть». Выбор раздела не меняет план, результат или его версию.

Mock API и localStorage нет. Несохранённый черновик существует только в памяти вкладки. Сохранение выполняется реальным backend. Графики — интерактивный SVG без библиотек/CDN: подсказки мышью и клавиатурой, переключатели серий/источников и фильтр годов. Фильтр меняет графики; KPI и годовая таблица явно остаются за весь горизонт расчёта.

## Ручная проверка

1. Откройте страницу заново: активен «Сценарий», поля не заполнены, KPI отсутствуют. «Перейти к проверке» без данных показывает критическую ошибку, расчёт недоступен.
2. «Загрузить JSON» → `results/plans/base-v1.json`: отображается имя файла и заполненная сводка, но расчёт не выполняется. Перейдите к проверке, затем нажмите «Рассчитать сценарий».
3. В результатах переключите BASE на MANDATORY_STRESS. Наведите указатель на точку или выделите её Tab, отключите серию в легенде, отключите источник и измените диапазон годов.
4. «Изменить исходные данные» → измените заказ: доступ к прежним результатам снимается. Повторите проверку и расчёт. Отрицательное значение блокирует расчёт. Исправить ошибку можно по ссылке рядом с её описанием.
5. «Создать новый» → «Заполнить вручную»: задайте название, заказы/брони, инвестиции и запас. Проверьте, что сводка меняется. Сохраните, создайте новый черновик, затем откройте сохранённый через карточку «Открыть сохранённый сценарий».
6. После расчёта откройте «Экспорт и отчёты»: сравните BASE / MANDATORY_STRESS, скачайте JSON плана, CSV и XLSX. JSON можно снова загрузить через единственную карточку импорта.
7. Попробуйте JSON с ошибкой синтаксиса и JSON с отрицательным объёмом. Первый выдаёт сообщение об ошибке формата, второй остаётся доступен для исправления в редакторе JSON. После ручных изменений JSON обязательно нажмите «Применить JSON».
8. Проверьте 1920×1080, 1600×900 и 1366×768; вертикальная прокрутка на небольшом экране нормальна, широкие подробные таблицы прокручиваются внутри своих блоков.

## Автоматические проверки

```powershell
python -m pytest
node --test tests/frontend-validation.test.cjs
```

Дополнительная браузерная проверка, если Playwright уже доступен в окружении (для приложения он не требуется):

```powershell
# При необходимости NODE_PATH указывает на каталог готовых node_modules с Playwright.
node tests/frontend-workflow.cjs
```

Сервер должен быть запущен. По умолчанию тест использует установленный Microsoft Edge в headless-режиме. `UI_BASE_URL` меняет адрес, `UI_BROWSER_CHANNEL` — браузер; `UI_SCREENSHOTS` задаёт папку диагностических снимков. Тест проверяет все три способа ввода, отсутствие авторасчёта, validation, переходы, графики, сохранение/открытие, поиск, выгрузки, INVALID_PLAN, ошибки сервера и состояния загрузки. Созданные тестом планы и выгрузки имеют уникальные имена и удаляются после проверки.

## Исполнимость и демонстрация жюри

`presentation.js` содержит единый компонент статуса. Его основной цвет зависит только от `result.feasible`: `true` — зелёный, `false` — красный, отсутствие результата — нейтральный. Число критических нарушений — количество `constraint_checks` с `ok: false` и `severity: hard`. Предупреждения отдельно выделены жёлтым, справочные проверки — синим. Backend не изменён.

В итогах сначала показаны статус и ключевые показатели. В «Экспорт и отчёты» порядок: статус, показатели, сравнение, основные нарушения, экспорт и подробные данные. В сравнении используются отдельные статусы из полного ответа `/api/compare`; компактная таблица содержит семь ключевых строк. Полные показатели и все годовые строки остаются в раскрываемом блоке.

`navigation.js` обновляет активный пункт по координатам секций, сохранённым при изменении размеров/раскрытии блоков. Пассивный обработчик прокрутки выполняет сравнение не чаще одного кадра. Короткие секции у конца страницы распределены по оставшемуся диапазону прокрутки. Таймеров переключения нет. Состав меню задан статически в HTML; верхняя панель учитывается при переходах.

План `tests/frontend-fixtures/inverse-plan.json` нужен только для приёмочной проверки. Настоящее ядро возвращает для него BASE: неисполним, 4 критических нарушения; MANDATORY_STRESS: исполним. Это следствие правил задачи: часть требований к сервису BASE в стрессе носит справочный характер. Ни результаты, ни статусы в приложении не подменяются.

Дополнительные тесты (сервер должен быть запущен):

```powershell
node --test tests/frontend-validation.test.cjs tests/frontend-presentation.test.cjs
node tests/frontend-workflow.cjs
node tests/frontend-clarity.cjs
```

Последний сценарий проверяет все 10 пунктов приёмки: пустой старт, импорт, четыре нарушения, противоположные статусы, предупреждения, понятные ошибки, прокрутку в обе стороны, переходы, задержку настоящего запроса и стабильность места под сравнением. Проверены 1920×1080, 1600×900 и 1366×768.


## Финальная проверка UX

`node tests/frontend-polish.cjs` проверяет семь оригинальных JSON пользователя из `tests/frontend-fixtures/01_…07_…`, счётчики, категории готовности, предупреждения, disabled:hover, поиск и непрерывную прокрутку вниз/вверх на 1920×1080, 1600×900 и 1366×768. Запускать при работающем сервере; переменные окружения такие же, как для других браузерных тестов.

Краткая готовность и подробная проверка используют `validatePlan`, а после ответа INVALID_PLAN — полученные ошибки. Зелёный здесь означает корректный формат, а не исполнимость. Предупреждения раскрываются без смены этапа. Подробные проверки скрыты, если нет строк; полный список сравнения доступен после ответа API. Разница обозначена STRESS − BASE, проценты — в п.п.; цвет нейтральный. Escape закрывает поиск, сохраняя текст, кнопка очистки зависит только от текущего значения поля.
